# florn 0.1.0

2026-10-20. The first release: the core on two Hosts. Phase 1 of the roadmap.

## What it is

- A deterministic kernel: logical time, a total order of events, activations that commit or discard, seeded streams, a trace with a chain of digests, replay (RFC 001).
- A guest contract and a Rust SDK: one core WebAssembly module with its manifest, strict lifting, recorded effects, fixed distributions (RFC 002).
- Module admission with limits: validation, the cost model, a budget, a stack height, memory, quotas; the same fault at the same point under every engine (RFC 003).
- The scenario manifest and package with a canonical hash (RFC 004).
- One Host core on two adapters: Wasmtime natively, and the browser's own engine in a worker, with guests reached without a JavaScript value in between (RFC 005).
- A headless runner, `florn`: `run`, `replay`, `admit`, `probe`.
- A browser test page with a service worker, served under the isolation headers and the policy of RFC 006.
- A conformance kit: fifteen scenarios with recorded digests, the verification rows of RFC 001, 002, 003 and 005 as tests, benchmarks with published figures, and eight fuzz targets.

Not in this release: any domain world, any user interface beyond the test page, checkpoints as a user feature. Release 0.2.0 is the network learning lab.

From source: `cargo install --path crates/florn` from a checkout of the tag, or `cargo install --git https://github.com/nabbisen/florn --tag 0.1.0 florn`. The guest SDK is `florn-guest = { git = "https://github.com/nabbisen/florn", tag = "0.1.0" }`.

## What was checked

Continuous integration on the release commit: rustfmt and clippy on both targets; the whole test suite on x86-64 Linux, AArch64 Linux and Apple Silicon; the conformance kit's scenarios in Chromium and Firefox on Linux and WebKit on macOS against the digests recorded natively; the licence and advisory gate; the dependency direction; the eight fuzz targets for three minutes each. The acceptance criteria AC-001 to AC-007 of the requirements specification are the kit's named tests. The verifier's own records of checklist items C1 to C13 are pending; the CI runs stand in for them until then.

## Security review (RFC 006 rule 5)

| Step | Answer |
|---|---|
| 1. Data flows, integrations, capabilities added | Since the RFCs were accepted: the run record and checkpoint files; the control interface over the worker's exports; the test page's service worker cache; the shipped scenarios served under `/scenarios`. No external integration; no capability beyond the files named on the runner's command line. |
| 2. RFC updated | RFC 005 rules 20, 22, 23, 29 and 32 to 35, RFC 006 rules 7 and section 7, RFC 003 rules 19 and 20 carry the changes; the threat model's zones stand (the worker holds the guests, Z3; the service worker is florn's own code caching served files, T4/C12). |
| 3. Controls of section 5 | C1 to C4, C9 to C11, C14 and C17 have their named tests in the kit and pass on every engine in CI; C16 is tested by the browser driver's instance-failure case; C12 is this release's immutable path and hashes; C13 is the gate; C15 waits for the 0.2 shell. |
| 4. Dependencies | `cargo deny check licenses advisories bans sources` clean on the release commit (the advisory database `cargo audit` reads); the allow-list of rule 6 unchanged. Wasmtime 48.0.7 closed RUSTSEC-2026-0378 and -0379 on 2026-10-20. |
| 5. Fuzzing | The eight targets of rule 7 ran three minutes each in the dispatched CI run and twenty seconds each locally after the last change; one crash was found and fixed before the release (a stream position overflow on a hostile checkpoint). |
| 6. Forbidden words | `ci/forbidden-words.sh` passes; no catalogue exists yet in 0.1. |
| 7. Served files' hashes | `SHA256SUMS` in the release assets and the release body. |

## Known limitations

- The browser Host assumes its instance ceiling by family (120 in Chromium-based browsers, 990 elsewhere) rather than probing at start-up, since a probe uses up what it measures.
- Export and restore of an actor are tested natively only; the control interface of 0.1 carries no restore command.
- The same guest source builds to different bytes on an AArch64 host than on x86-64 (the runs give the same digests); the kit ships the built modules, and the figures report each machine's own build.
- `florn admit` names the module `module` in its log line; a name arrives with control interface version 2.
