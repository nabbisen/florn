# florn 0.3.0

2026-10-31. The third release: depth. Phase 3 of the roadmap.

## What it is

On the network learning lab of 0.2.0, unchanged in meaning:

- Checkpoints (RFC 009 section 2): the Host takes one every 10,000 handled events and on request, keeps them under a memory budget with the start never dropped, lists them, restores one in place, exports one as a `.florn-checkpoint` file after a preview, and starts a run from such a file with the identity checked field by field. The runner's `resume`, `--checkpoint-at` and `--checkpoint-out`; a checkpoint crosses the two Hosts both ways in the kit.
- Backward navigation and detail by replay (section 3): "Go to…" and "Step to here" move back to an instant by restoring the nearest checkpoint and executing forward; the interventions after it are undone and said, re-applied or discarded by the person; a trace window the Host no longer holds is produced by re-execution through the run's own instances; the browser Host keeps only the records since the last checkpoint.
- Branching (section 4): a new run from the current instant with the parent's inputs so far, the parent ended and its record kept, the parent named in the branch's record and in the inspector.
- Cost-model version 2 (RFC 010): florn's own metering pass, version 1's units charged into a local of the function and the budget global touched only before calls, before a loop's back-edge, before a return and at a function's end; the default from the owner's decision on the measured figures; version 1 kept for its records and on request.
- Actor swapping (RFC 009 section 5): on request, a resident set smaller than the actor count; the least recently activated actor leaves as exported state and returns into a fresh instance before its activation; the digest is the resident run's; the status line says "swapping" with the counts.
- The application's depth (sections 6 and 7): the controls for going back, branching and checkpoints; origin storage as a visible cache of what the person opened, saved, imported or exported; a module imported from a file shown with both hashes before it is placed; a Component refused with the reason; the installable application; "limited by" memory and swapping from the Host's own figures; the address carries no content.
- The BGP subset and its lab (RFC 011): external sessions over links with the four-state machine, the three RIBs and the decision by local preference, AS-path length, MED and router id; the learning lab `bgp-lab` with its story in both languages and `bgp-outside`.
- Wasmtime 48.0.8 (two advisories of 2026-10-30 against 48.0.7, on paths florn never enables), with every recorded digest unchanged.

Not in this release: the native shell, a decoder as a sandboxed module, the circuit and control domain. Release 0.4.0 is the circuit and control domain.

Continuous integration on the release commit: rustfmt and clippy on both targets, the shell included; the whole test suite on x86-64 Linux, AArch64 Linux and Apple Silicon, the kit's checkpoint, navigation, branching, swapping, cost-model, retention and BGP tests among it; the conformance kit's twenty-seven scenarios in Chromium and Firefox on Linux and WebKit on macOS against the digests recorded natively, under cost-model version 2 and, for five of them, under version 1 as well, with the cross-Host checkpoint and branch checks and the lab through pools of one, two and the full capacity; the journeys J1 to J5 and the procedures P1 to P4 in the three browsers, with the installable manifest, the language on every panel, the keyboard bound, the offline start, the frame figure, the address after every journey and the one-origin network log; the catalogues in both languages with every key present; the shell's exports; the licence and advisory gate; the dependency direction; the RFC index; the book; the eight fuzz targets for three minutes each on the dispatched run named under Figures, the metering pass under both cost-model versions among them.

## Compatibility with 0.2.0

- A guest written for 0.2.0 builds unchanged against `florn-guest` 0.3.0 and `florn-guest-network` 0.3.0. A module built with the 0.2.0 SDK is admitted by a 0.3.0 Host.
- Scenarios, packages and run records of 0.1.0 and 0.2.0 are read by 0.3.0 unchanged; a record of either replays under its own cost-model version when its modules are supplied. A 0.3.0 record carries the cost-model version it ran under and, for a branch, a `[parent]` table.
- The control interface stays at version 1 with additions (RFC 009 section 8, `export { kind: parent-record }`, `new-run { residency }`); a 0.2.0 Host refuses the additions as unknown, and the 0.3.0 application reads a 0.2.0 Host's answers.
- New runs admit under cost-model version 2: the admitted hashes differ from 0.2.0's, the trace digests do not, except the hostile scenarios whose fault is a trap between two checks, recorded for version 2.
- The shipped scenarios' digests are unchanged across the engine update and the SDK rebuild; the modules' hashes changed, as said above.

## Known limitations

- The browser Host assumes its instance ceiling by family (120 in Chromium-based browsers, 990 elsewhere); swapping lets a scenario beyond it run, at the cost of a swap per activation at worst.
- Cost-model version 2 meters a trap between two checks without the local's remainder; an activation that completes is metered exactly as version 1.
- A port's `local-pref` and `med` of the BGP guest travel as router parameters of `port=value` pairs, the contract exposing no per-port parameter beyond the cost.
- The application replays a run record; it does not play back a trace. The native shell is a later release.
- Going back within an instant restores to the instant's boundary; a trace window asked for mid-instant is answered from the kept records alone.
